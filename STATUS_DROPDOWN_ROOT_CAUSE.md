# Referral status dropdown investigation

## Result

No status-dropdown generation defect exists in the current running code. The reported behavior was not reproducible on either the existing service at `127.0.0.1:8000` or a fresh PHP server at `127.0.0.1:8111` using the same authenticated browser session and database.

There is therefore no line of current code preventing `Accepted`, `Rejected`, or `Completed` from rendering. The observed behavior must have come from a different referral/page state or code instance; it is not produced by the checked-in referral-review page.

## Trace

| Stage | Source | Finding |
| --- | --- | --- |
| Database read | `includes/customer_referrals.php:96-100` | `business_referral()` selects `r.*`, including `customer_referrals.status`, by referral ID and owning business ID. |
| PHP current status | `business/referral_view.php:24-30` | The returned database row is stored in `$referral`; no later code overwrites `$referral['status']`. |
| Transition generation | `business/referral_view.php:68` | `$allowedStatuses` is generated exclusively by `permitted_referral_statuses((string) $referral['status'])`. |
| Workflow helper | `includes/customer_referrals.php:12-20` | A `match` returns `Submitted → Under Review`, `Under Review → Accepted/Rejected`, `Accepted → Completed`, and terminal empty arrays. |
| HTML rendering | `business/referral_view.php:78-80` | The only options are generated by `foreach ($allowedStatuses as $item)`. There is no extra filter, cache, enum lookup, switch, or client-side option removal. |
| Browser JavaScript | `business/referral_view.php:83-94` | JavaScript submits the selected status and reloads the page; it never changes the dropdown options. |
| Database update | `business/referral_view.php:46-61` | The selected allowed status is validated, written by `UPDATE customer_referrals SET status = ?`, then recorded in `referral_status_history`. |

The status enum/constants are consistent:

- `CUSTOMER_REFERRAL_STATUSES` at `includes/customer_referrals.php:6`
- `customer_referrals.status` at `database/module5_customer_referrals.sql:24`
- `referral_status_history.status` at `database/module5_customer_referrals.sql:44`

## Browser verification

Using a temporary local authenticated business session:

1. Opened referral #1 while it was `Submitted`; the page rendered `Under Review`.
2. Submitted `Under Review` through the page's normal JSON POST endpoint; reload rendered `Accepted` and `Rejected`.
3. Submitted `Accepted` through the same endpoint; reload rendered `Completed` with the completion-modal marker.
4. Opened existing `Completed` and `Rejected` referrals; both rendered no update dropdown and were read-only.

The same `Accepted → Completed` rendering was also confirmed on the existing port-8000 server, so that server was not caching an older dropdown implementation.

## Fix

No dropdown-logic change was required or made because the current code already generates the expected next statuses and browser testing confirms it. The temporary debug instrumentation was removed after verification.

For any recurrence, inspect the referral URL/ID and open the page with the temporary trace pattern above before modifying the transition helper: the dropdown is determined only by the `customer_referrals.status` value for that exact referral.
